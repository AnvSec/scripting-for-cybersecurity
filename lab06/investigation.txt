The parsing issue can still be explained: in a line containing
"Failed password for invalid user NAME from IP", a pipeline that takes
the word immediately after "for" returns "invalid", not NAME. The
finished script skips the two words "invalid user". A temporary,
clearly synthetic test used username deploy to verify this; that test
is not evidence of a real login and is not included in case/ or intel/.

Part 8.3 - report on access.log
report-web.txt reports 0 failed-password events, no most common SSH
source and no targeted SSH usernames. This is correct for the searched
SSH message, but it is not a general web-attack analysis. The web log
has 80 requests; 22 contain sqlmap (27% with shell integer arithmetic,
or 27.5% without truncation). To analyse HTTP activity, count the first
field as the client IP and examine URLs, status codes and user agents.
The script explicitly says that zero SSH events does not rule out other
activity.

Part 8.4 - firewall blocks and SSH events
The supplied firewall log contains:
BLOCK 203.0.113.10 -> 10.0.0.10:22
BLOCK 198.51.100.24 -> 10.0.0.10:22
BLOCK 203.0.113.200 -> 10.0.0.30:3389

Two possible explanations for SSH sources appearing in both logs:
1. The SSH attempts happened before the firewall began blocking them.
2. The SSH events concern a different destination or network path from
   the specific destination/path where these firewall blocks occurred.
These are possibilities, not confirmed causes. The firewall entries
have no timestamps, and the SSH lines do not include the destination IP,
so the supplied files cannot establish exact timing or path correlation.
